## 1. 成功标准先行

### 1.1 本文档完成标准

1. 准确记录当前 `EventBus` / `EventScope` / `EventHandlerRegistry` 的可观察行为。
2. 明确 V2.1 后续实现的行为决策表，避免实现阶段隐式改契约。
3. 明确“零 GC”的边界：只承诺**稳态 `Publish` 热路径**，不把诊断 API 误当热路径。
4. 明确 `handler` 异常隔离是相对当前行为的兼容性变化，必须有诊断出口。
5. 明确 `EventScope` 生命周期仍由 owner 显式管理，不把 scope 隐式交给 `ModuleHost`。
6. 明确 `EventHandlerRegistry` 诊断应依赖 Source Generator 生成结构化元数据，而不是运行时扫描。
7. 明确 ADR-0020 红线与非目标。

### 1.2 后续实现完成标准

1. `Publish<T>` 在“事件类型已有订阅列表、没有结构变更触发扩容”的稳态路径不再执行 `ToArray()` 或等价数组快照分配。
2. 保持当前派发顺序：订阅者按订阅顺序同步调用。
3. 保持当前重入语义：派发中 `Subscribe` / `Unsubscribe` 只影响下一次 `Publish`。
4. 单个 `handler` 抛异常不阻断后续 `handler`；派发结束后通过明确的诊断/上报机制暴露异常。
5. 无论 `handler` 是否抛异常，派发中挂起的 add/remove 都必须在 `finally` 或等价保证中 flush，不能让队列永久滞留。
6. `EventScope.Dispose` 继续满足逆序、幂等、吞解绑异常并继续清理。
7. `EventHandlerRegistry` 至少具备结构化诊断的设计落点：事件类型、handler 标识、来源 manifest/assembly、注册顺序、ApplyAll 结果/失败信息。
8. Shadow csproj / `ServerProject` 编译继续 0 error；Core 不引用 UnityEngine。

## 2. ADR-0020 约束与非目标

V2.1 必须继续遵守 ADR-0020（路线 C：纯客户端服务框架）：

- Runtime/Core 不引用 `UnityEngine`。
- 不做运行时程序集扫描 / 反射扫描注册。
- 不引入第三方依赖。
- 不恢复 ECS / Entity / Aspect / SystemBase。
- 不恢复服务端抽象（`INetServer` / `IConnection` / `ITickLoop` 等）。
- 不恢复 `IPlugin` / `IPlugPoint` / `IPluginHost`。
- 不引入 DGame 风格弱类型 `int eventId` + 多参数重载作为 Core 公共事件总线。
- 不把 `EventBus` 做成 Unity 生命周期对象，不新增 Editor 面板或可视化调试器。
- 不做跨线程事件队列，不做异步事件总线。

本次迭代的目标是把现有强类型 `IEventBus` 做深，而不是换一套事件系统。

## 3. 当前代码基线

### 3.1 `EventBus`

当前实现：`MyTryGetFramework/Assets/MyTryGetFramework/Runtime/Core/Event/EventBus.cs`。

关键事实：

- 存储结构是 `Dictionary<Type, object>`，每种事件类型对应一个 `List<Action<T>>`。
- `Publish<T>` 在有订阅者时执行：

```csharp
var snapshot = list.ToArray();
for (int i = 0; i < snapshot.Length; i++)
{
    snapshot[i].Invoke(evt);
}
```

- 因此每次有订阅者的 `Publish` 都会分配数组快照；无订阅者时直接返回，不分配该 snapshot。
- 派发顺序是订阅顺序。
- `IEventBus` 公开 API 均约束 `where T : struct`，V2.1 默认保留该强类型 struct event 契约。
- `Subscribe<T>(null)` 抛 `ArgumentNullException`。
- 同一事件类型重复订阅同一个 delegate 抛 `InvalidOperationException`。
- `Unsubscribe<T>(null)`、事件类型不存在、handler 未订阅：静默返回。
- 成功移除最后一个 handler 后，该事件类型会从字典中删除。
- 派发中增删依赖 `ToArray` snapshot：当前 Publish 不受影响，只影响下一次 Publish。
- `handler` 异常不隔离：第一个抛出的异常会原样传播并停止后续 handler。
- `GetSubscriberCount<T>()` 是诊断 API。
- `GetEventTypes()` 返回 `new List<Type>(_handlers.Keys)`，会分配；返回顺序不应作为契约。
- `Clear()` 是 `internal` 实现细节，不属于 `IEventBus` 生命周期能力。

对应测试：`EventTests.cs` 已覆盖重复订阅、派发中增删 next-publish-only、异常传播且停止派发、诊断 count/types。

### 3.2 `EventScope`

当前实现：

- `MyTryGetFramework/Assets/MyTryGetFramework/Runtime/Core/Event/IEventScope.cs`
- `MyTryGetFramework/Assets/MyTryGetFramework/Runtime/Core/Event/EventBusScopeExtensions.cs`

关键事实：

- `EventScope` 独立于 `IEventBus` / `ModuleHost`，内部只保存一组 unsubscriber action。
- `bus.CreateScope()` 只是创建新的 `EventScope`，不与 bus 状态绑定。
- scoped subscribe 当前是扩展方法：先 `bus.Subscribe(handler)`，成功后 `scope.Register(() => bus.Unsubscribe(handler))`。
- 因此 scoped subscribe 继承普通 Subscribe 的 null、重复订阅与异常语义。
- `Dispose()` 首次调用时设置 `IsDisposed = true`，按注册逆序执行解绑动作，吞掉单个解绑异常并继续清理，最后清空列表。
- 重复 `Dispose()` 是 no-op。
- `Register` 在 scope 已 Dispose 后会立即执行传入 unsubscriber 并吞异常，不保存它。
- 当前已 Dispose scope 下调用 scoped subscribe：最终不会残留 handler，但会经历一次 Subscribe/Unsubscribe；如果同一 handler 已订阅，可能先触发普通 Subscribe 的重复订阅异常。
- `ModuleHost.Shutdown()` 当前不自动 Dispose 外部 `EventScope`，也不通过公开契约清理 EventBus 订阅。

对应测试：`EventScopeTests.cs` 已覆盖 Dispose 逆序、幂等、解绑异常吞掉、scope 自动退订、多 scope 隔离、多事件类型同 scope。

### 3.3 `EventHandlerRegistry`

当前实现：`MyTryGetFramework/Assets/MyTryGetFramework/Runtime/Core/Event/EventHandlerRegistry.cs`。

关键事实：

- 本质是静态 `List<Action<IEventBus>> _registrations`。
- `Register(null)` 抛 `ArgumentNullException`。
- `Register` 当前不去重，同一个 registration delegate 可以重复注册。
- `ApplyAll(bus)` 按注册顺序执行所有 registration。
- `ApplyAll(null)` 抛 `ArgumentNullException`。
- 某个 registration 抛异常时，当前实现不会捕获，会中断后续 registration 并向 `Bootstrap.CreateHost` 调用链传播。
- 诊断只有 `Count` 与 `Snapshot()`。
- `Snapshot()` 返回 `_registrations.ToArray()`，会分配。
- 当前没有事件类型、handler 标识、来源 assembly/manifest、注册顺序元数据、ApplyAll 结果、失败信息或按事件类型查询。
- `Bootstrap.CreateHost` 在 `AssemblyManifestRegistry.ApplyAll(host)` 之后执行 `EventHandlerRegistry.ApplyAll(host.EventBus)`；Source Generator 生成的 `[EventHandler]` 注册会订阅到该 host 的 EventBus，但 registry 本身不管理 unsubscribe/scope 生命周期。

## 5. 零 GC Publish 与重入策略

### 5.1 “零 GC”的精确定义

V2.1 的“零 GC”只指：

> 对某个已有订阅者的事件类型，在订阅列表已经稳定、内部容器不扩容、无诊断 snapshot 的情况下，`Publish<T>` 热路径不产生托管堆分配。

不承诺零分配的路径：

- `Subscribe` 创建事件类型列表或扩容。
- `Unsubscribe` 触发内部 pending 结构首次分配或压缩。
- 派发中 pending add/remove 队列扩容。
- `GetEventTypes()`。
- `EventHandlerRegistry.Snapshot()`。
- 未来 registry metadata snapshot。
- 测试/诊断/统计导出。

### 5.2 不允许的实现方式

- 不能直接删除 `ToArray()` 后遍历原 `List<Action<T>>`，否则派发中增删可能导致跳过 handler、重复调用、索引错乱或破坏 next-publish-only 语义。
- 不能为了避免分配改成弱类型 `int eventId` 总线。
- 不能依赖 Unity `Profiler` 或 Runtime Unity API 作为 Core 实现的一部分。
- 不能用运行时反射扫描来恢复 handler 元数据。

### 5.3 推荐实现方向（不在本文落代码）

可选内部结构：

1. **pending add/remove + 派发深度计数**  
   派发中不修改 active handler 列表，而是记录到 pending 队列；最外层安全边界统一 flush。

2. **版本化 handler 表**  
   每次结构变更增加版本；派发使用稳定版本边界，结构变更延后到下一轮可见。

3. **双缓冲列表**  
   active buffer 用于当前派发，pending buffer 用于下一轮可见状态。

无论采用哪种方式，必须满足：

- 当前 Publish 的可见 handler 集合稳定。
- 派发中新增 handler 不参与当前 Publish。
- 派发中移除 handler 不影响当前 Publish 的既定快照语义，只影响下一次 Publish。
- flush 必须在 `finally` 或等价机制中执行。
- 嵌套 Publish 的 flush 边界必须明确：建议按事件类型维护 dispatch depth，最外层该事件类型 Publish 结束后 flush；若采用全局 depth，也必须写入测试。

## 6. handler 异常隔离策略

### 6.1 当前问题

当前 `EventBus` 是 fail-fast：任一 handler 抛异常会停止后续 handler 并把异常传播给调用者。

引入 pending add/remove 后，如果仍然让异常直接跳出且没有 `finally` flush，会出现 DGame `EventDelegateData` 类似风险：延迟增删队列可能永远不 flush，事件系统状态被污染。

### 6.2 V2.1 目标行为

V2.1 目标从 fail-fast 改为异常隔离：

- 单个 handler 抛异常，不阻断后续 handler。
- 派发期间捕获的异常必须可诊断，不能静默吞掉。
- pending flush 必须执行。

### 6.3 待实现时最终确认的上报形态

以下三种均可满足“隔离”，但可观察行为不同；实现前需在 issue 中选定一种：

| 方案 | 行为 | 优点 | 风险 |
|---|---|---|---|
| A. 记录诊断，不抛 | Publish 永不因 handler 异常抛出 | 业务事件最稳 | 错误可能被忽视，必须有 logger/diagnostic |
| B. 继续派发，末尾抛 `AggregateException` | 所有 handler 都执行，最后把异常交给调用者 | 保留调用方感知 | Publish 仍会抛，调用方需处理 |
| C. 错误回调/接口 | 异常进入 `IEventBusDiagnostics` 或 logger | 可观测且不污染 Publish API | 需要新增诊断接口 |

本文档倾向 **C（诊断出口）或 B（聚合异常）**，不建议无诊断地吞异常。

## 7. EventScope 生命周期策略

V2.1 把 `EventScope` 提升为事件生命周期的一等设计语言，但不把所有 scope 强行交给 `ModuleHost`。

### 7.1 owner 显式管理

推荐用法：

- Module 持有自己的 `EventScope`，在 `Shutdown()` Dispose。
- Procedure 持有自己的 `EventScope`，在 `OnExit()` Dispose。
- UI Window / View 持有自己的 `EventScope`，在关闭/销毁时 Dispose。
- 测试中继续使用 `using (var scope = bus.CreateScope())`。

### 7.2 不做 host-owned scope

V2.1 不默认新增：

- `ModuleHost.CreateScope()` 自动托管 scope。
- `ModuleHost.Shutdown()` 自动清理所有外部 scope。
- 模块基类或 UI 基类。

原因：当前 Core 没有统一 Module base class / UI 生命周期；强行托管会制造混合所有权。等 V2.3 UI、V2.5 Scene 等真实 owner 出现后，再设计 owner-specific helper。

### 7.3 可保留的未来候选

未来可考虑：

```csharp
// 示例方向，不是 V2.1 必做 API
public interface IEventScopeOwner
{
    EventScope EventScope { get; }
}
```

或 Source Generator 为 `[EventHandler]` 生成带 owner metadata 的注册信息。但 V2.1 不实现。

## 8. EventHandlerRegistry 诊断策略

### 8.1 当前缺口

当前 registry 保存黑盒 `Action<IEventBus>`，因此无法可靠回答：

- 注册了哪个事件类型？
- handler 方法是谁？
- 来源哪个 assembly / manifest？
- 注册顺序是什么？
- 是否已经 Apply 到某个 host？
- ApplyAll 哪一步失败？
- 是否重复注册？

不能通过运行时反射扫描补洞，因为这违反 ADR-0020 的方向，也不可靠。

### 8.2 设计方向

后续 Source Generator 应生成结构化元数据，Core 只消费生成产物。

示意方向：

```csharp
public readonly struct EventHandlerRegistrationInfo
{
    public readonly Type EventType;
    public readonly string HandlerId;
    public readonly string SourceAssembly;
    public readonly string ManifestId;
    public readonly int Order;
}
```

Registry 可新增兼容 overload：

```csharp
// 保留旧路径，兼容旧生成代码
public static void Register(Action<IEventBus> registration);

// 新路径，由新 Source Generator 生成 metadata
public static void Register(EventHandlerRegistrationInfo info, Action<IEventBus> registration);
```

注意：以上只是设计方向，不在本文档任务中实现。

### 8.3 ApplyAll 异常策略

当前 `ApplyAll` 是 fail-fast：某个 registration 抛异常会中断后续注册并传播。

V2.1 默认不改变该启动期失败语义。若未来要提供 ApplyAll 结果快照，需要另行明确：

- fail-fast + 记录失败点；或
- collect-and-continue + 返回失败列表；或
- collect-and-throw aggregate。

不能在实现中顺手改变 Bootstrap 启动失败语义。

## 9. 与 Source Generator 的兼容

V0.9.5 已有 `[EventHandler]` Source Generator 路线：生成代码通过 `EventHandlerRegistry.Register(...)` 收集注册委托，`Bootstrap.CreateHost` 后统一 Apply。

V2.1 必须保持：

- 旧生成代码仍可调用 `Register(Action<IEventBus>)`。
- 新生成代码可调用 metadata overload。
- Generator 继续使用编译期信息生成注册，不做运行时扫描。
- Runtime/Core 不引用 Roslyn，不引用 UnityEngine，不引用第三方库。
- metadata 只用于诊断与查询，不改变事件派发热路径。

## 11. 参考框架吸收点

来自第二轮源码复核：

- AlicizaX `ServiceScope`：迭代期间 `_isIterating`，Register/Unregister 入 pending changes，迭代结束 flush；索引化 swap-remove 可作为 O(1) 注销技巧。
- AmaniDawn/DGame `EventDelegateData`：`m_isExecute + addList/removeList` 延迟增删，证明该模式适合事件派发。
- 两者共同问题：缺少 handler 异常隔离；DGame 在异常时存在 dirty/pending 不 flush 的风险。

TryGet 的吸收方式：

1. 只吸收纯 C# 的重入安全延迟增删模式。
2. 不吸收 AlicizaX 的 MonoBehaviour root / 静态 AppServices / UniTask / Cysharp.Text。
3. 不吸收 DGame 的静态 ModuleSystem / 弱类型 int eventId / Unity 业务模块。

## 13. Verdict

V2.1 推荐从 **EventBus 零 GC Publish + 重入安全 + 异常隔离** 开始实现。

本 PRD 刻意把范围压在事件系统核心：

- 热路径只优化 `Publish`。
- 生命周期只强化 `EventScope` 使用边界，不引入 host-owned scope。
- 诊断只定义 registry metadata 方向，不一次性做完整工具链。
- 所有实现必须保持 ADR-0020：纯 C#、强类型、无 UnityEngine、无运行时扫描、无第三方依赖。

进入实现前，应先把本文拆成 `.scratch/<feature>/` issues，并逐 Iter 验收；不要在一个提交里同时改 EventBus、Source Generator、UI/Scene 生命周期与诊断工具。
